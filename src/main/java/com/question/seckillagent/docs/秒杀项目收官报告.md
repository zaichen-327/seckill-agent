## 一、项目概况

项目起点是已有的开源原型（aiyuyang/spring-boot-seckill），不直接用原代码；在此基础上独立加了登录、秒杀结果查询、三个运维接口和发布预热模块，每个都经过 Apifox 验证，JMeter 压测 440 QPS 零超卖，本地部署跑通、代码开源在 GitHub。但这不是服务真实用户的线上生产系统，不能说成"生产上线"。

## 二、秒杀核心链路

### 2.1 防超卖：Lua 脚本原子扣减（2026-10-23）

lua/seckill.lua：库存 key 不存在返回 -1，库存 ≤0 返回 -2，否则原子减 1。SeckillService.stockDeduct 经 DefaultRedisScript<Long> 执行，验证 2→1→0→-2、DEL 后 -1。

### 2.2 秒杀接口（2026-10-23）

POST /seckill/doSeckill/{activityId}/{token}。链路：① token 校验（先删后用防重放）② 活动 + 时间窗口校验（不存在 / 未开始 / 已结束）③ Lua 扣库存（-1 记日志"活动未预热"，用户看"活动未开始"；-2 为"已售罄"）④ 发 MQ。

### 2.3 RabbitMQ 异步下单（2026-10-24）

生产者 confirm + returns 回调，失败回补库存；消费者原生 Message + Channel 手动 ACK，解析失败进死信，insert 成功 ack，DuplicateKey（重复订单）回补 Redis 库存后 ack，其他异常进死信。v1 曾因框架转换期异常导致消息永久 Unacked，改为 v2 原生消息解决（面试素材：毒消息处理）。

### 2.4 限流与结果查询（2026-10-25）

限流：doSeckill 第一行 checkRateLimit，固定窗口 key seckill:limit:{activityId}:{userId}，60 秒内超过 10 次报"操作过于频繁，请稍后再试"。结果查询 GET /seckill/result/{activityId}：有订单→"秒杀成功"，库存 key 为 null→"活动未开始"，库存 >0→"排队中"，否则"已售罄"。前端每 2~3 秒轮询。

### 2.5 验证码（2026-10-29 修复并发缺陷）

初版验证码按活动单槽存储（seckill:captcha:{activityId}），并发用户互相覆盖。修复：generateCaptcha 返回 {captchaId（UUID 去横线）, image}，答案存 seckill:captcha:{captchaId}，按 captchaId 取用后删除。验证码与秒杀 token TTL 均为 600 秒。

### 2.6 登录切片（2026-10-31 ~ 11-01，7 步全验证通过）

seckill_user 表 + BCrypt 注册 / 登录；JWT（jjwt 0.9.1，HS256，24 小时过期，subject 为 userId，claim 带 username + role）；拦截器校验 Authorization: Bearer token，UserContext ThreadLocal 存 userId（afterCompletion 必须 clear 防串号）；doSeckill / result 的 userId 改从 UserContext 取；秒杀 token key 按（活动，用户）隔离。401 事件：spring-security-crypto 间接带入 Security 过滤链，application-dev.yaml 里同时排除 SecurityAutoConfiguration 与 ManagementWebSecurityAutoConfiguration 解决。

小轮回归通过：5 用户（test1~test5）全绿，订单 5 条 user_id 各异，Redis 库存恰好 -5，死信队列为空。

## 三、压测结果（2026-10-30）

JMeter 5.6.3。小轮：1 线程 × 20 循环全链路，20 单、0 重复、死信为空，串行 0 超卖。大轮：500 线程 / ramp-up 1 / 循环 1，平均 26ms、最大 85ms、Error% 0、Throughput 440.1/s，Redis 2000→1500，0 超卖。

简历口径：峰值 440 QPS（核心链路，不含验证码和 token 发放），即 Lua 扣库存 + MQ 异步落库，不写成全链路 QPS。验证码是预发放的，洪峰只打 doSeckill，大轮不需重测验证码 + token。

教训：重启后未重建活动，JMeter 一片绿但 doSeckill 响应体是"活动不存在"——看 body 的 code，不看 HTTP 状态（接口统一 Result，HTTP 状态恒为 200，业务 code 在 body 里）。

索引优化：uk_user_activity 为 (user_id, activity_id)，按 activity_id 单独 COUNT 走了 type=index；加 idx_activity_id 后 type=ref、Using index（覆盖索引）。

## 四、运维 Agent

### 4.1 Phase 1：暴露工具（2026-11-01 ~ 11-08，4 个接口，Apifox 全验证通过）

- **① GET /ops/metrics**：运维指标总览。每维独立 try/catch 填 null/false；N+1 由本人亲手抓出改批量（订单 1 条 GROUP BY + 库存 1 次 mget，IO 固定 5 次与活动数无关）。
- **② GET /ops/activities**：活动列表，状态口径 NOT_STARTED / RUNNING / ENDED，与 metrics 一致。
- **③ GET /ops/orders**：订单列表，limit 默认 20、上限 100，按 create_time 倒序。注意：该接口不按用户过滤，一个账号能查到全部用户的订单。
- **④ POST /ops/activities/{id}/publish**：第一个写操作。confirm=true 落在接口层，重复发布 hasKey 拒绝"活动已发布"。

Stale key 坑（2026-11-08，面试素材）：schema.sql 每次启动 DROP 重建活动表、id 循环复用，但 Redis 的 seckill:stock:{id} 不跟着清，新活动会被误判"已发布"。根治：SeckillActivityServiceImpl.create() 里建活动成功后 DEL 掉该 id 的旧库存 key（开发清脏 key，生产为空操作），hasKey 防线保留。

### 4.2 Phase 2：Python Agent 本体（2026-11-12 ~ 11-13）

Agent 本体在本地 VS Code 写，代码在仓库内 agent_vs/（tools.py + agent.py + agent_api.py）。模型是租的（API 调 DeepSeek），不训练；Agent 是自己写的 Python 程序。

- **工具封装**：tools.py：login + get_metrics + get_activities + get_orders + publish_activity，全部验证通过。publish 初版 URL 漏 /{activity_id} 致 404、Python 取 data["code"] 报 KeyError，补上后通过。
- **ReAct**：agent.py：手写 ReAct 循环（未用 LangChain），openai SDK 调 DeepSeek，key 走 .env；TOOLS 为四个工具的 function-calling schema；run_agent 最多 5 步，本身 return 答案文本。防幻觉验证通过：问天气正确拒绝编造。
- **两个 bug（本人发现）**：messages 每次在 run_agent 内重建导致"确认"对不上号，修法是 messages 挪到 __main__ 创建并持久传；工具报错抛到 main 致崩溃，修法是 try/except 包住 call_tool，报错当观察结果喂回模型。
- **交互**：登录只做一次，token 传进 run_agent；/exit 循环问答。__main__ 的写死固定值（真密码、写操作）已改 input() 现场输入、写操作移出每次都跑的测试流程。

### 4.3 可观测性：OpenTelemetry（2026-11-15）

TracerProvider + ConsoleSpanExporter。三个埋点：agent.run（记 agent.question）、llm.call（记 prompt/completion/total token 数）、tool.call.{name}（失败记 error）。验证：两问两 trace，parent_id 链对得上。不做 Jaeger/OTLP、自动埋点、messages 截断。

### 4.4 FastAPI 服务与前端联调（切片 6，2026-11-18）

agent_vs/agent_api.py：POST /chat，收 {question, session_id}，token 从 Authorization 头拿，服务自己不登录；会话存内存 dict，重启清空；CORS 放行 localhost:5173。Apifox 调 /chat 返回 answer 通过；前端运维聊天页提问经 Vite 代理 → FastAPI 8000 → Agent → Java 8080 全链路通过。Vite 代理曾因 /agent 前缀未去掉报 404，修法是加 rewrite 去掉 /agent 前缀（nginx 定稿里用尾斜杠方案避免重犯）。

git 误操作事件（2026-11-18）：在 IDEA 撤销提交时点错，未提交的 agent_api.py 与前端两处修复丢失；已提交内容无损；按原样重建并重新提交。教训：改完先提交再动 git。

## 六、前端与部署

### 6.1 前端：Vue 3 + Vite（2026-11-16，用户定：不想学前端，要一个直接解压能用的压缩包）

Vue 3 + Vite + Router + Axios，无 UI 库、无 Pinia。5 个页面：登录双入口（用户 / 管理员）、注册、活动列表、秒杀详情（2000ms 轮询结果）、运维聊天 /ops。另有活动管理页（/admin/activities，仅 ADMIN 可见）：列表调 GET /ops/activities，新建调 POST /ops/activities，发布预热调 POST /ops/activities/{id}/publish。

登录双入口：都调 /user/login，管理员入口若 role 不是 ADMIN 则报错不进；前端路由守卫 + 后端拦截器双重保障。

2026-11-18 当天修复三处：① 发布过的活动按钮改成不可点击并显示"已预热"（判断依据是 metrics 里 redisStock 是否为 null，不能写 !redisStock，因为卖光后是 0 也是已发布）；② 验证码图不显示（easy-captcha 的 toBase64() 自带 data:image/png;base64, 前缀，前端又拼了一遍，双前缀导致图片裂开）；③ 秒杀后库存不减少（前端显示的 availableStock 是数据库的值，秒杀只扣 Redis，消费者 insert 订单后从来没改过数据库的 availableStock；修法是消费者 insert 成功后加一条 SQL 把 availableStock 原子减 1，重复订单那支不减）。

### 6.2 后端角色切片（切片 0，2026-11-16）

seckill_user.role（默认 USER）+ 注册默认 USER + JWT 带 role claim + 拦截器校验 /ops/* 只放 ADMIN。登录返回改版曾误报完成：只验 /ops/metrics 没查出 login 仍 return token；后改成返回 Map{token, role, username}（接口 + Controller 同步改），管理员登录才真正通过。教训：改返回形状必须看一眼登录接口的 data；下游三处（前端拆包、Apifox 提取路径、Python tools.py 取值）都因这次改版出过坑。

### 6.3 接口分离（2026-11-18）

起因：前端管理员没法在界面上直接建活动、发布预热，联调得回 Apifox；且 POST /activity 和 POST /activity/publish/{id} 在 /activity/* 白名单里、没登录都能调，是个权限口子。分法：用户接口（/activity/list、/activity/{id}、/seckill/*）vs 管理员接口（/ops/*，创建、发布预热、运维数据，全走 ADMIN 校验）。后端已完成并 Apifox 验证通过：POST /ops/activities 已加（复用 create，DEL 旧库存 key 已在 Service 里），旧的 POST /activity 和 POST /activity/publish/{id} 已删（调旧接口报 404）。

另补 GET /seckill/orders/my（2026-11-18）：JWT 鉴权，userId 只从 UserContext 取、绝不从 query 接；按 create_time 倒序；活动名批量查防 N+1；limit 上限 50。Apifox 验证时曾因 jwt_token 变量装的是整个 data 对象（提取路径还是旧的 $.data，应为 $.data.token）报"登录已过期"，改提取路径后通过。

### 6.4 nginx 上线（切片 8，2026-11-18）

nginx Windows Stable 1.30.6 解压到 D:\nginx；前端 npm run build 生成 dist/（98 模块，1.11s）；配置 seckill-frontend-nginx.conf 放进 nginx/conf/nginx.conf（替换默认 server 块）；start nginx 后打开 http://localhost（不用写端口，浏览器默认 80）能进页面；验证三样全通——test1 登录、活动列表显示、运维 Agent 提问出答案（/agent → FastAPI 8000 代理通）。

## 八、踩过的坑（面试素材）

- **RabbitMQ**：毒消息：v1 消费者在框架转换期异常，消息永久 Unacked；改为 v2 原生 Message + Channel 手动 ACK。
- **Stale key**：schema.sql 每次启动 DROP 重建活动表、id 循环复用，Redis 旧库存 key 残留致新活动误判"已发布"；根治是建活动成功后 DEL 旧 key。
- **验证码**：验证码按活动单槽存储，并发用户互相覆盖；改为按 captchaId（UUID）隔离。
- **401**：spring-security-crypto 间接带入 Security 过滤链致注册 401；同时排除两个 AutoConfiguration 解决。
- **登录返回**：只验 /ops/metrics 没查出 login 仍 return token；改返回形状必须验响应体本身，且同步改所有下游取值处（前端、Apifox、Python）。
- **login() 取值**：tools.py 的 login() 返回整个 data 字典而非 token 字符串，三个工具拼 Bearer 全报 str+dict 错误；用户口头"改好了"不算数，以实际运行结果为准。
- **Agent 误诊**：Agent 工具选对但结论错三处（夹具误读、未预热误判、key 过期误判）；工具对 ≠ 答对。
- **git 误操作**：在 IDEA 撤销提交时点错，未提交的 agent_api.py 与前端两处修复丢失；改完先提交再动 git。
- **校园网**：校园网到 GitHub 的 git push 经常连接重置，换手机热点一次即过；下载 JDK 时同理，关 VPN / 用热点。
- **库存不同步**：消费者 insert 订单后从不改数据库的 availableStock，页面库存永远不动；修法是 insert 成功后原子减 1，减 DB 与 Redis 回补互斥、不会冲突。
